# 一文读懂 [AnalyticDB MySQL](https://help.aliyun.com/zh/analyticdb/analyticdb-for-mysql/product-overview/what-is-analyticdb-for-mysql) 过滤条件智能下推原理

> 过滤条件下推是数据库优化的经典手段，但在 AnalyticDB MySQL 的存储计算分离架构下，全下推到存储层并不总是最优解。新一代智能下推模块基于准确的统计信息和代价模型，自动决策哪些条件该下推、哪些不该，让用户不再纠结于是否下推的 [SQL 调优](https://help.aliyun.com/zh/analyticdb/analyticdb-for-mysql/user-guide/performance-tuning/)。

---

## 一、前置知识：过滤条件下推

在我们的常规认知中，过滤条件肯定是推得越靠近底层越好——将尽可能多的过滤条件更贴近数据源，以使查询时能跳过无关的数据。在 AnalyticDB MySQL 中，由于存储计算分离架构，谓词下推就是把所有能推的谓词都推到存储节点上去做。

如下图，所有的过滤条件都推到存储节点上去做，这样减少了后续算子的计算量，也减少了中间网络传输的数据量。谓词下推带来了很多的好处，基本上所有数据库，都会把谓词下推作为他们重要的优化功能。

---

## 二、全下推到存储层的弊端

但是过滤条件下推到存储层一定会快吗？

为了弄清这个问题，先来看一下 AnalyticDB MySQL 的存储节点的索引结构。ADB 目前默认是**全索引**，即会为所有列创建索引，并且支持多个条件同时走索引，快速多路合并，能够在毫秒级别找出满足条件的结果集。

下图展示了一个表上多个过滤条件的索引查找过程。可以看到是每一列都会查找索引，最后将 RowIds 做交并差集运算。

### 2.1 不下推 VS 下推

了解完索引结构后，我们构造一个简单的例子，来说明过滤条件下推到存储之后却变慢的情况。

假设一个代价模型：每一行扫索引的代价是 A，每一行取明细以及数据传输的代价是 B，计算层每一行过滤的代价是 C。

```sql
create table user (age int, id int);
select count(*) from user;                        -- 结果 10,000
select count(*) from user where age > 18;          -- 结果 9,000
select count(*) from user where id < 10;           -- 结果 20

-- 考虑如下 SQL
select * from user where age > 18 and id < 10      -- 结果 10
```

- **常规计划代价**：10,000A + 10,000A + 10B（两列分别查索引的代价 + 取明细以及数据传输的代价）
- **id 列不下推计划代价**：10,000A + 20B + 20C（一列查索引代价 + 取明细以及数据传输的代价 + 计算层代价）

可以看出如果 `10B + 20C < 10,000A` 的话，id 列不下推计划是更优的计划。

### 2.2 可优化场景

默认情况下，优化器会将所有带索引的列下推存储，从而减少读取至计算引擎的数据。但是仍存在几种场景不建议使用索引过滤数据：

- **谓词选择率高，且谓词条件多**：数据经过过滤后返回的数据仍然很多，那么使用索引进行数据过滤然后取交集的效果不一定好
- **磁盘 IO 压力大**：如果用户业务的查询特征是占用较多的 IO 资源，或者数据写入较多导致占用了较多 IO 资源，那么使用索引进行数据过滤时，存在磁盘 IO 资源的争抢，过滤效果也可能较差
- **过滤谓词中带有复杂操作**：比如字符串比较、LIKE 操作等，会对存储节点产生较大的资源消耗，如果其他条件过滤后数据不多，不下推会对整体性能更加友好

## 三、智能下推

所以为了优化 ADB 上述场景的性能，同时也为了避免 ADB 研发人员和用户耗费精力使用不下推 hint 来进行 SQL 调优，在 ADB 新版本推出了**智能优化功能**，优化器基于准确的统计信息，在 ADB 中智能控制过滤条件是否下推到存储节点，让用户不用再纠结于是否下推的 SQL 调优，加速用户查询，把简单交给用户。

### 3.1 术语定义

- **conjunction**：把过滤条件按照最外层的 AND 拆分之后的单元叫做 conjunction。比如 `((A & B) | C) & D & E` 就是由 `((A & B) | C)`、`D`、`E` 三个 conjunction 组成的。conjunction 是是否下推到存储的最小单元，一个 conjunction 里面的条件要么都下推，要么都不下推。
- **selectivity**：谓词的过滤度。如果有 100 行数据，满足 `A > 10` 的数据是 10 行，那么 `A > 10` 的 selectivity 是 10%。
- **connector**：ADB 优化器支持多个 connector，既可以支持 ADB 本身存储引擎，也可以支持 OSS 外表。不同的 connector 需要不同的处理。

### 3.2 实现流程

**A series of rules**：ADB 优化器原有的一系列过滤条件下推规则，会尽量把 filter 一路推到 table 上方，推到距离存储节点最近的地方，然后下面的工作便交给了智能下推模块。

**Pretreatment（预处理）**：
- **短路优化**：在模块开始会粗略判断整个表扫描的开销，比如是个很小的表，那就快速跳过，以减少后续流程处理的额外开销
- **表达式转化**：应用布尔代数定律，尽量将过滤条件转换为 AND 连接。拿一个简单的例子来说，`(A & B) | (C & D)` 是无法做到部分下推、部分不下推的，但是将其转换为 `(A | C) & (A | D) & (B | C) & (B | D)` 之后，便可以做到部分下推。这一步进行了限制，不会盲目转化，因为转换之后的表达式变长，可能会导致 codegen 超限等影响

**CalcSelectivity**：根据直方图等精准的 statistics，调用 ADB 优化器中的 Cardinality Estimation 模块去为每个 conjunction 计算 selectivity 和相应的 reliability。这个模块依托 ADB 优化器中精准的统计信息以及完善的基数估计，提供高质量的选择率，为后续的代价计算以及下推方案的选择，提供准确的输入。

**Connector Cost Model**：存储层自定义的代价模型，定义了根据 selectivity 计算出来的 cost 满足一定条件的过滤条件不会下推。这种分离的模式使得接入 ADB 的别的存储层，有智能下推的需求，也可以简单实现 connector cost model，便可以实现智能下推的功能。

**FilterPushDownSelection**：这个模块负责将所有的 conjunction 以及其 selectivity 和 reliability 输入给相应的 connector cost model，然后以 conjunction 为最小单元枚举下推组合，模型算出代价，最后根据代价去选择开销最低的下推方案。这样下来，ADB 便由之前的全下推，演变为现在的智能下推。

## 六、结构化数据表

### 6.1 全下推 vs 不下推 代价模型

| 场景 | 公式参数 | 代价公式 | 适用条件 |
|------|---------|---------|---------|
| 常规全下推 | A=索引扫描代价, B=传输代价 | 10,000A + 10,000A + 10B | 索引扫描开销低，选择率低 |
| 部分列不下推 | A=索引扫描代价, B=传输代价, C=计算层过滤代价 | 10,000A + 20B + 20C | `10B + 20C < 10,000A` |

### 6.2 代价模型参数详解

| 参数 | 含义 | 影响因素 |
|------|------|---------|
| A | 每一行扫索引的代价 | 索引结构、数据量、列数 |
| B | 每一行取明细及数据传输的代价 | 网络带宽、数据行大小 |
| C | 计算层每一行过滤的代价 | CPU 性能、过滤条件复杂度 |

### 6.3 不建议使用索引过滤的场景

| 场景类型 | 特征描述 | 原因分析 |
|---------|---------|---------|
| 高选择率 + 多谓词 | 过滤后返回数据仍然很多 | 索引取交集效果差 |
| 磁盘 IO 压力大 | 查询/写入占用较多 IO | 索引查找存在 IO 资源争抢 |
| 复杂谓词操作 | 字符串比较、LIKE 操作 | 存储节点资源消耗大 |

### 6.4 智能下推核心术语

| 术语 | 说明 | 示例 |
|------|------|------|
| conjunction | 按最外层 AND 拆分后的过滤单元 | `((A&B)\|C)&D&E` → `((A&B)\|C)`, `D`, `E` |
| selectivity | 谓词过滤度（满足条件的行数占比） | 100 行满足 10 行 → 10% |
| connector | 存储连接器（ADB 引擎/OSS 外表） | 不同 connector 需要不同处理 |

### 6.5 智能下推模块流程

| 模块名称 | 功能描述 | 输入 | 输出 |
|---------|---------|------|------|
| A series of rules | 原有下推规则，将 filter 推到 table 上方 | 原始过滤条件 | 尽可能下推的过滤条件 |
| Pretreatment | 预处理（短路优化 + 表达式转化） | 过滤条件 | 优化后的 AND 连接条件 |
| CalcSelectivity | 计算每个 conjunction 的选择率和可靠性 | 过滤条件 + 统计信息 | selectivity + reliability |
| Connector Cost Model | 存储层自定义代价模型 | selectivity | cost 判断是否下推 |
| FilterPushDownSelection | 枚举下推组合，选择最优方案 | conjunctions + selectivity + cost model | 最优下推方案 |

### 6.6 预处理模块详解

| 预处理操作 | 原理 | 效果 | 限制 |
|-----------|------|------|------|
| 短路优化 | 粗略判断表扫描开销，小表快速跳过 | 减少后续处理开销 | 无 |
| 表达式转化 | 布尔代数定律，OR 转 AND | 实现部分下推、部分不下推 | 表达式变长可能 codegen 超限 |

### 6.7 全下推 vs 智能下推对比

| 对比维度 | 全下推模式 | 智能下推模式 |
|---------|-----------|-------------|
| 决策依据 | 固定规则（有索引就下推） | 统计信息 + 代价模型 |
| 下推单元 | 单个谓词 | conjunction（AND 拆分单元） |
| 灵活性 | 无，全部下推 | 高，按代价选择 |
| 人工调优 | 需使用不下推 hint | 自动决策，无需人工 |
| 适用场景 | 索引扫描开销低的场景 | 所有场景，自动适配 |
| connector 支持 | 仅 ADB 存储引擎 | 多 connector（ADB + OSS 等） |
