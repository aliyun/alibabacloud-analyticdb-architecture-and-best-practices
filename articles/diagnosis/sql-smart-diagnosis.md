# 重磅发布：新一代云原生数据仓库 AnalyticDB「SQL 智能诊断」功能详解

> SQL 是一种简单易用的业务逻辑表达语言，但随着扫描数据量和查询复杂度的增加，查询性能会变得越来越慢。[AnalyticDB For MySQL](https://help.aliyun.com/zh/analyticdb/analyticdb-for-mysql/product-overview/what-is-analyticdb-for-mysql) 为用户提供了高效、实时、功能丰富并且智能化的「SQL 智能诊断」功能，降低用户使用成本，提高使用效率。

---

## 一、背景：SQL 调优为什么难？

想要对 SQL 进行调优，往往需要关注以下几个部分：

1. **需要了解引擎架构**：用户需要对 SQL 引擎的架构特点有一定的了解，才能和业务的数据分布特征以及业务场景特征完美结合，来进行数据建模，从而设计出符合 SQL 引擎架构特点的表结构。
2. **SQL 特征差异较大**：即席查询的 SQL 往往变化较大，包括参与 Join 的表个数、Join 条件、分组聚合的字段个数以及过滤条件等。
3. **数据特征差异较大**：用户的数据分布特征会随着业务特征的变化而改变，如果一直按照最初的建模方式和 SQL 语句，无法保障发挥出 SQL 引擎的最大优势。

基于此，AnalyticDB For MySQL（以下简称 ADB）为用户提供了「SQL 智能诊断」和「SQL 智能调优」功能（后者将在后续版本发布），提供 SQL [性能调优](https://help.aliyun.com/zh/analyticdb/analyticdb-for-mysql/user-guide/performance-tuning/)的思路、方向和具体方法。

## 二、发现慢查询

用户要定位慢查询，首先需要找到慢查询。ADB 的用户控制台提供了多样的方式来帮助用户，例如「甘特图」和「查询列表」等，都可以在多个维度进行检索，帮助用户快速定位慢查询，诊断工具确保用户可以进行最近两周的全量查询检索和分析。

### 2.1 甘特图

用户可以通过「集群控制台」→「诊断与优化」→「SQL 诊断」进入 SQL 智能诊断功能。


甘特图以图形化的方式形象地展示了查询在 ADB 实例上的执行顺序：

- 每个色块表示一条查询
- 色块左侧为查询的提交时间，右侧为结束时间
- 色块的相对长度表示某条查询的执行时间
- 色块的颜色只是为了区分不同的泳道


通过甘特图，用户可以非常直观地看到：
- 当前时间范围内执行耗时较长的查询
- 哪些查询是在并行执行以及并行执行的时间段
- 哪些查询受到了某条 Bad SQL 的影响
- 色块的密集度可以直观判断 ADB 实例压力较大的时段

### 2.2 查询列表

甘特图能够以直观的方式体现出查询之间的时间相关性，但当用户选择的时间范围较大，甘特图中的色块会密集分布不容易分辨。此时用户可以使用诊断工具中的查询列表功能。

查询列表提供了多达 10 余项查询级别的重要指标，例如数据库名、用户名、客户端 IP、耗时、消耗内存以及扫描量等。


**高级检索能力**提供了三种类型的检索方法：

1. **模糊检索和精确检索**：根据 SQL 中的关键字进行模糊匹配，或在确定查询 ID 的情况下精确检索。
2. **字符串类型的检索条件**：自动识别出所选时间范围内使用的数据库名、用户名、客户端 IP 以及资源组等，以下拉框形式供用户选择。
3. **数值类型的检索条件**：用户可自由选择检索的指标单位，例如 KB、MB、GB 等，不需要手动换算。

同时提供了查询列表的下载功能，下载后的慢查询可以在 Excel 等工具中进行更多自定义的慢查询治理和分析。

## 三、诊断慢查询

### 3.1 查询在 ADB 中的执行流程

在介绍 ADB 执行流程前，需要了解三个基本概念：

- **Stage**：ADB 中的查询会根据是否产生 Shuffle 被切分为多个 Stage 来执行，一个 Stage 就是执行计划中某一部分的物理实体。
- **Task**：Task 是一个 Stage 在某个 Executor 节点上的执行实体，多个同类型的 Task 组成一个 Stage。
- **Operator（算子）**：ADB 的最小数据处理单元，ADB 会根据算子所表达的语义或算子间的依赖关系，决定使用并行还是串行执行。

以一个典型的分组聚合查询为例：

```sql
SELECT COUNT(*), SUM(salary)
FROM employee
WHERE age > 30 AND age < 32
GROUP BY sex
```

在 ADB 内部，首先由前端的 Controller 节点接收 SQL 语句请求，进行语句解析和语法分析（Parser），最后使用优化器（Optimizer）生成最终的执行计划。整体执行计划会根据 Stage 的划分原则被切分为子计划（Plan0、Plan1、Plan2），分别被下发到对应的节点上。

其中子计划 Plan2 会并行地在 4 个计算节点上以 Task 实例的形式处理数据，首先执行数据的扫描和过滤，然后执行数据的局部聚合，处理完之后的数据会根据 sex 字段 Repartition 到下游的计算节点（Stage1 的节点），按照子计划 Plan1 的要求执行数据的最终聚合。最后，数据由 Stage0 的节点汇总并返回到客户端。


### 3.2 逻辑执行计划 vs 物理执行计划

和典型的数据仓库一样，ADB 的执行计划一般分为「逻辑执行计划」和「物理执行计划」：

**逻辑执行计划**——宏观层面了解查询的处理流程：
- 基于规则的执行计划（RBO）判断过滤条件是否可以下推
- 基于代价的执行计划（CBO）判断多表关联时的顺序等
- 只包含 Stage 级别的执行统计信息

**物理执行计划**——微观层面了解每个算子的处理性能：
- 包含算子间的数据处理流图和算子的执行统计信息
- 可以精确看到某个 Join 算子或聚合算子占用的内存
- 可以看到过滤算子过滤前后的数据量

| 对比维度 | 逻辑执行计划 | 物理执行计划 |
|----------|-------------|-------------|
| 关注层面 | 宏观：查询整体处理流程 | 微观：每个算子的处理性能 |
| 优化方式 | RBO 判断过滤下推、CBO 判断 Join 顺序 | 算子级性能分析 |
| 统计粒度 | Stage 级别 | 算子级别 |
| 可查看信息 | Stage 执行统计 | 算子内存占用、数据过滤前后量等 |

ADB 的「SQL 智能诊断」功能提供了一个**逻辑执行计划和物理执行计划的融合视图**，用户既可以从宏观层面了解查询的处理流程，也可以从微观层面了解每个算子的处理性能。

### 3.3 SQL 自诊断功能

虽然提供了融合的和分层的执行计划来帮助用户分析查询的性能问题，但在两类场景中用户仍会遇到困难：

- **ADB 的初级使用者**：面对 ADB 的执行计划，往往不知道优化的重点在哪里，无从下手。
- **ADB 中的复杂 SQL**：复杂的 SQL 往往涉及几百张表的连接操作，Stage 个数会达到几百个以上，算子个数更是会达到上千，执行计划图非常大。


针对以上问题，ADB 在执行计划图中加入了 **SQL 自诊断** 能力，将专家经验以规则的形式体现在执行计划中。SQL 自诊断通过「Query 级别诊断结果」、「Stage 级别诊断结果」、「算子级别诊断结果」三层来展示诊断结果和优化建议。

#### 案例一：内存消耗较大的查询

通过慢查询检索工具搜索到一个内存消耗较大的查询，点击「诊断」打开该查询的诊断页面，切换到「执行计划」页签：


1. 查询级别诊断结果已判断出当前查询是内存消耗较大的查询
2. 点击按内存排序，Stage[1] 占用了当前查询 87% 以上的内存比例
3. 点击 Stage[1]，诊断工具会自动聚焦到执行计划树的 Stage[1] 位置
4. 提示当前 Stage1 内部有个算子占用内存较大
5. 进入 Stage[1] 内部，根据内存排序可以看到 Join[317] 算子占用了整个 Stage 99% 以上的内存


点击 Join[317] 算子，算子诊断结果提示：在构建 Hash 表用于 Left Join 时占用了较大的内存，诊断结果还提供了官方的[调优文档](https://help.aliyun.com/zh/analyticdb/analyticdb-for-mysql/user-guide/performance-tuning/)链接。

#### 案例二：Stage 级别数据倾斜

根据耗时排序后，Stage[10] 的耗时比例最大：


点击执行计划图中的 Stage[10]，诊断结果栏显示两类诊断结果：
- **Stage 诊断**：当前 Stage 的输出数据有倾斜，并告知倾斜的字段
- **算子诊断**：提示表扫描存在倾斜

初步判断当前 Stage 输出数据倾斜是因为扫描了一个数据倾斜的表导致的。

进入 Stage[10] 内部，根据耗时排序可以看到 TableScan 算子耗时最大：


点击 TableScan 算子，诊断结果显示：这张表由于数据分布字段选择不合适，存在严重的数据倾斜问题，同时提供相关的官方[调优文档](https://help.aliyun.com/zh/analyticdb/analyticdb-for-mysql/user-guide/performance-tuning/)。根据调优文档调整为合适的分布字段，即可减少表数据倾斜对查询性能的影响。

## 九、后续规划

### 9.1 我应该调优哪些 SQL？

用户在打开诊断调优页面时，面对实例上运行的上万甚至上千万条 SQL，虽然可以通过耗时、内存消耗或者扫描量等进行排序来初步筛选，但欠缺一个特定诊断结果的视角：

- 哪些 SQL 是数据扫描倾斜的？
- 哪些 SQL 是索引过滤不高效的？
- 哪些 SQL 是 Stage 输出倾斜的？
- 哪些 SQL 是分区选择不合理的？

后续会提供给用户一个从**特定诊断结果维度**进行分析的工具，一次性地解决某个特定问题。

### 9.2 我的 SQL 有问题，和建表方式不优有关吗？

后续会把「数据建模诊断结果」和「查询诊断结果」关联，用户通过数据建模的诊断结果即可快速知道不良的表结构影响了哪些 SQL，同时反过来也可以通过某条 SQL 的诊断结果知道哪些表需要优化。两类诊断结果联动调优，可以从根源上解决实例的查询性能问题。
